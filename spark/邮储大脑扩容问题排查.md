# **Spark任务大面积变慢及Executor申请超时问题复盘**

## **一、问题概述**

近期集群扩容部分 Kubernetes Node 节点后，Spark 作业运行出现异常，表现为：

· Spark 作业启动阶段耗时明显增加；

· Executor 申请时间延长，大量任务在 Executor 启动阶段等待；

· 部分 Spark 作业出现 Executor 注册超时、Heartbeat 超时等异常；

· 集群运行一段时间后问题逐渐扩大，影响范围增加。

受影响环境：

· Spark 版本：2.4

· Driver 模式：YARN Cluster Mode

· Executor 动态资源分配：开启（Dynamic Resource Allocation）

· NodeManager：采用nodemanager on k8s的部署方式 

· DataNode：部署于独立 Hadoop 集群

· Spark Shuffle Service：启用

进一步观察 YarnAllocator 日志发现：

...

# **三、排查过程**

## **1.排查ResourceManager情况**

由于报错最开始时，报出driver无法连接clustermanager，导致申请executor失败，排查ResourceManager相关情况：  
网络方面各网卡无丢包情况，RM总连接数维持在100个左右，负载不高：

![](file:///C:\Users\ADMINI~1\AppData\Local\Temp\ksohtml23236\wps3.png) 

RM内存使用方面，查看jstat，内存使用情况无异常，FULLGC次数较少，无长时间STW，但元空间内存使用达95%以上，但综合其他集群元空间使用情况也可达95%以上，且fullgc较少，判断为RM节点正常：

![](file:///C:\Users\ADMINI~1\AppData\Local\Temp\ksohtml23236\wps4.png) 

## **2****. 排查Driver JVM资源问题**

GC检查：查看 卡住Driver gc情况：

· Full GC次数少；

· 单次Full GC耗时约1秒；

· 无明显Young GC异常；

· 无持续Stop-The-World。

结论：driver端内存使用情况比较正常，Driver JVM内存压力；GC导致RPC线程暂停。

## **3****. 排查Driver线程状态**

使用 jstack 分析 Driver 线程。执行两次jstack <driver_pid> > driver.dump，两次间隔15分钟，重点关注：

· RPC线程；

· Netty线程；

· YarnAllocator线程；

· Executor注册相关线程。

分析发现：

Netty RPC、Spark UI线程、dispatcher、Shuffle-server等网络相关线程存在两次jstack卡住状态不变化的情况，这些是导致网络通讯超时、sparkui长时间不更新问题的根源。

例如：

nioEventLoopGroup

sun.nio.ch.EPollArrayWrapper.epollWait

io.netty.channel.nio.NioEventLoop.run

说明：相关线程处于正常等待网络事件状态。

![](file:///C:\Users\ADMINI~1\AppData\Local\Temp\ksohtml23236\wps5.jpg)![](file:///C:\Users\ADMINI~1\AppData\Local\Temp\ksohtml23236\wps6.jpg)![](file:///C:\Users\ADMINI~1\AppData\Local\Temp\ksohtml23236\wps7.jpg) 

同时未发现有Full GC停顿。

初步判断，问题不在Driver JVM内部，而是网络相关配置存在问题，同时，默认使用的是nio通讯方式，建议项目组评估spark.rpc.io.mode spark.shuffle.io.mode 修改为EPOLL，提高网络传输效率，同时设置spark.speculation=false减少避免执行，并排查网络相关配置。

最终项目组排查网络配置时发现新扩容的节点k8s的dns/hosts配置缺失，导致该问题。
